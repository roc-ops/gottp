# Changelog

All notable changes to GoTTP will be documented in this file.

## [Unreleased]

### Fixed: YANG submodules, and which calls validate (baseline cluster 7, #175, #58)
- **`YANGModules` accepts submodules (#175).** A `submodule NAME { belongs-to PARENT { ... } }` file in `Files` (or `URLs`) failed the whole load with `module name not found in YANG content`, so nothing was validated. Now each submodule is registered under its `belongs-to` module, as yangson and pyang do. The parent's `include` statements resolve, and `yang="PARENT:container/..."` paths into a submodule's content validate under the parent's name or prefix. `Modules` already loaded them; both are now tested with a parent that includes one submodule per command.
- **A submodule's parent must be loaded.** A module that includes a missing submodule fails to load, naming it. A module that includes another module's submodule fails to load (RFC 7950 7.1.6). A submodule whose parent is not loaded is ignored, as yangson ignores it. A path into it gives `module or prefix 'PARENT' not found; submodule S belongs to PARENT, which is not loaded`.
- **`Parse` does not validate (#58).** `CompiledTemplate.Parse` and `Runtime.Parse` ran YANG validation and threw the results away. Now they ignore `ParseOptions.YANGModules` and don't load the modules, so a module that fails to load no longer fails `Parse`. Use `ParseWithValidation` for validation results.
- **Every `yang=` group has a `ValidationResults` entry**, even one that produced no records. Its path is still checked: a path that names no schema node is an error, and otherwise the entry is valid. A nested group with no records gets its entry under its plain name.
- **With several inputs, a group's validation results merge** into its one entry: valid only if every input's records are, with every input's errors. Before, the last input's results replaced the others. A path error is reported once.
- **`ParseStream` with `YANGModules` set and a `yang=` group returns `*TemplateNotStreamableError`.** It never validated, so the modules were silently ignored. The error names each `yang=` group. Pass no `YANGModules` to stream without validation.
- New: `yang.ExtractModuleHeader` returns whether content is a module or a submodule. `yang.MergeResults` merges two validation results. `yang.ExtractModuleName` also returns a submodule's name.

### Fixed: a line's regex ends at `{{ _start_ }}`/`{{ _end_ }}`, as in TTP (baseline cluster 2, #136, #121)
- **A line stops at a `_start_` or `_end_` variable (#136).** Python TTP's `regex_deleteVar` cuts the line's regex there, with the whitespace before it. gottp matched anything after it (`.*?`), so `interface {{ _start_ }}` also matched `interface Gi1`, `interface {{ name }} {{ _start_ }}` matched `interface Gi1 extra`, and `ospf {{ _start_ }}` matched `ospf3 0`. Now each matches only its own text: records that such a line used to start or end on the wrong line change.
- **A variable after the indicator isn't captured from the data** (`interface {{ _start_ }} {{ name }}`), as in TTP. On a `_start_` line it gets no value. On an `_end_` line with no capture left (`exit {{ _end_ }} {{ w }}`), TTP gives every variable of the line, `_end_` too, the whole matched line with a newline first (`"\n exit"`, indent and trailing spaces kept), and runs its functions on it; gottp now does the same. Such a variable also makes the line an ordinary line, so it no longer ends the group. `GetWarnings()` names each such variable once, says what it gets, notes that a `default()` value still applies, and suggests moving the indicator or using it as a function (`{{ name | _start_ }}`; for `_line_`, a named variable such as `{{ rest | ORPHRASE | _start_ }}`).
- **A run of mixed spaces and tabs in a template line is one `[ \t]+`, as in TTP.** gottp replaced runs of spaces and runs of tabs separately, so `interface \t{{ name }}` needed at least two blanks before the name (`[ \t]+[ \t]+`) and didn't match `interface Gi1`, and `interface \t{{ _start_ }}` kept one `[ \t]+` after the cut. Template lines with only spaces, or only tabs, between words are unchanged; `_exact_space_` lines keep their blanks as they are.
- **`{{ _start_ | re(...) }}` stays a gottp extension.** A `_start_`/`_end_` variable with its own `re()` isn't cut and matches the regex; TTP ignores the `re()`.
- #121 (an indented standalone `{{ _end_ }}` matched any blank line) was already fixed by #33; this adds its repro. `test_slack_answer_3` (listed under #100) now passes.
- TTP's `_end_` off-by-one (#139) is not part of this change.

### Added: the `_headers_` indicator (baseline cluster 6, #68)
- **`{{ _headers_ }}` parses fixed-width tables, as in TTP.** The text before it is the header row, and each header becomes a variable that captures its column by position. The regex is TTP's `regex_headers` regex: the first `columns-1` columns are exactly as wide as their header, column `columns` is 1 character up to that width, later columns are 0 up to their width, and the last column takes the rest of the line. `columns` defaults to the header count minus 2; set it with `{{ _headers_ | columns(N) }}`. The line starts a record. Values are stripped.
- **TTP's quirks are kept.** Each header runs `exclude(header)`, so the header row is dropped, and so is any row that has a header's name inside that header's column (`Namex` under `Name`). A row of only spaces matches with empty values; an empty line doesn't. A tab in the header row's indent counts as 4 characters. Text after `{{ _headers_ }}` is ignored.
- **Where TTP raises, gottp works:** one or two headers (`columns` is at least 1), headers that aren't Python identifiers (`Port-Id`, `1st`), and headers named `None`, `True` or `False` work.
- **New compile errors:** another variable on the `_headers_` line, no headers before it, two headers with the same name, a header named `ignore`, `_start_`, `_end_`, `_line_`, `_exact_` or `_exact_space_` (TTP treats these as plain keys, but gottp would drop the column or change how records join), and `columns` without an integer argument.

### Fixed: YANG paths under a choice, and choice semantics (baseline cluster 7, #124, #122)
- **A `yang=` path names data nodes (#124).** choice and case are not data nodes (RFC 7950 7.9), so `yang="p:c/bc"` now resolves `container bc` inside `choice ch { case b { container bc } }`; it failed with `YANG path not found`. At each step a data node is looked up first, descending through choices and cases; the schema-node form `p:c/ch/b/bc` still works. A path that ends on a choice or case (`p:c/ch`) is an error that lists the data nodes under it. A "not found" error now lists the data-node children, sorted, rather than the raw schema children.
- **Choice semantics, as yangson (TTP's `validate_yangson`) applies them (#122).** A `mandatory true` choice is satisfied by a node from any one of its cases; it was reported missing (`Required field 'ch' is missing`) for every item. With no case present the error is `Required choice 'ch' is missing: ...`. Mandatory nodes inside the case that is present are now checked (they weren't checked at all), including nested choices. Data from more than one case of a choice is an error (`Fields of choice 'ch' come from more than one case: ...`), as yangson's `member-not-allowed`. **This can reject data that validated before**: a record with nodes from two cases, or one that lacks a mandatory leaf of its case.
- **`length` counts characters, not bytes (#122)**, as RFC 7950 9.4.4 and yangson do: `"ééé"` meets `length "1..3"`.
- Required-field errors now come in sorted order.

### Fixed: blank data lines and `default()` captures (baseline cluster 1, #162, #64, #65, #91)
- **Blank data lines are matched, as in TTP (#162).** A data line that is empty or holds only spaces and tabs was skipped before matching unless the template line was a start or end indicator. Now it is skipped only for a template line whose regex can't match it (worked out once, when the template compiles), so `{{ x | _line_ }}`, `re(".*")` and `re("[ ]+")` match it, and `_line_ | joinmatches` keeps it: `desc a  \n  \nmore `. `Parse` and `ParseStream` agree.
- **A blank line is matched as it is.** A start or end indicator line used to see a blank line as `""`. Now it sees the spaces too, so an indented `  {{ _start_ }}` matches a line of at least two spaces but not an empty line, and a standalone `{{ _start_ }}`/`{{ _end_ }}` line keeps its indent in the regex, as TTP's `\n  [\t ]*` does.
- **`default()` no longer captures the space before it (#64).** `ip address {{ ip | default("none") }}` on `ip address 1.1.1.1/24` gives `"1.1.1.1/24"`, not `" 1.1.1.1/24"`. The same goes for `set()` variables and `_start_`/`_end_` variables on a line with text: the space before them is now optional instead of removed (`[ \t]*`), which only changes what they capture. Source maps and dynamic paths built from such values change with them (`pwr_sdp.8243`, not `pwr_sdp. 8243`).
- **`default()` without a regex stays a gottp extension.** It keeps the `.*?` regex, so a trailing `{{ col | default("") }}` still matches an empty or missing last column and text with spaces, where TTP (`WORD`) drops the line. A line made only of `default()` variables doesn't match blank lines. See `test/comparison/KNOWN_DIFFERENCES.md`.
- #65 (the `default()` value when its line is absent) and #91 (a group with no matching lines emits its defaults) were already fixed on main; this adds the #65 repro. The last case listed under #91, `test_group_default_referencing_variable_parent_group_no_re_two_inputs`, fails because of #70 (several unnamed inline `<input>` tags), and is now listed there.

### Changed (breaking: captured values keep trailing whitespace, as in TTP, #33)
Data lines are no longer stripped of trailing spaces and tabs before they are matched. Python TTP 0.10.1 keeps them (its line regex is `\n<line>[\t ]*(?=\n|\r\n)`), so gottp now does too:
- **A greedy capture keeps the trailing spaces**: `{{ x | re(".*") }}` on `a 1  ` gives `"1  "`, and `re("[a-zA-Z0-9 ]+")` on `vlan 2 name X ` gives `"X "`. They were trimmed.
- **A trailing `{{ ignore(".*") }}` matches a line with trailing whitespace** (`Core Freq : 1200MHz   DDR Freq : 600MHz  `); it didn't match at all.
- **`_exact_space_` lines allow trailing whitespace**, as TTP appends `[\t ]*` whether or not `_exact_space_` is set: `a  {{ x | _exact_space_ }}` matches `a  1  `.
- **A template with no tags keeps its first line's indent**: ` Core {{ c }}` matches ` Core 1` but not `Core 1`. The whole template was trimmed, so the first line matched at any indent. Leading blank lines are still dropped.
- Source maps: a match's `EndCol` now includes the line's trailing whitespace, as Python's match span does.
- `\r` is still trimmed from data lines, so with CRLF input `.*` doesn't capture the `\r` as it does in TTP (see `test/comparison/KNOWN_DIFFERENCES.md`).

### Added: Python type methods for match variables (refactor F2, #36)
A match variable function that isn't a match function now runs the value's own Python 3.12 method or attribute of that name, as Python TTP 0.10.1's `getattr` fallback does (`ttp.py:2464`). The methods are Go ports in `internal/pymethod`: every `str` method except `encode`, the `int`/`bool` methods `bit_length`, `bit_count`, `conjugate`, `as_integer_ratio` and `is_integer` and attributes `real`, `imag`, `numerator` and `denominator`, the `float` methods `is_integer`, `conjugate`, `as_integer_ratio` and `hex` and attributes `real` and `imag`, `list.count`, `index` and `copy`, and `dict.get`, `keys`, `values`, `items` and `copy`. See "Python type methods" in the match variable functions docs.
- **True or False filters the match**, any other result replaces the value: `{{ v | isalpha }}`, `{{ v | title }}`, `{{ v | zfill(9) }}`, `{{ v | to_int | bit_length }}`, `{{ v | split(",") | index("b") }}`. They were skipped.
- **Python 3.12 semantics, Unicode included:** full case mappings (`upper("straße")` is `STRASSE`), final sigma, Python's `title`, the `is*` character classes and its whitespace set. The Unicode tables are generated from Python 3.12 (`internal/pymethod/gen_unicode.py`) and checked against it for every code point.
- **A method that raises fails the parse**, as in TTP, which catches only `AttributeError`: `index("z")` with no `z` (`ValueError`), `center("a")` (`TypeError`). `Parse` returns the exception. A name the value's type doesn't have keeps the value, as before.
  - **Only on a line TTP evaluates.** TTP's `run_re` runs a group's start patterns on the whole input and its other patterns only from the first start match on (not at all when nothing matches a start line), its ordinary patterns only up to the line of the last `_end_` match, and a child group's patterns only inside its parent's region. A raise on any other line no longer fails `Parse` or `ParseStream`. `ParseStream` emits no record once a raise is known to fail the parse.
  - A child group's patterns, and a group's ordinary patterns, no longer match the line of the last `_end_` match that narrows the region: TTP's line regexes need the newline after the line, which falls outside the region.
- **`!r` in `format` escapes as Python's `repr` does**: a character `str.isprintable` rejects (NBSP, `\x85`, `\u2028`, ...) is written `\xa0`, `\u2028` or `\U000e0001`.
- **Such a name no longer warns as unknown.** A name that is a method of no type still does. Methods that change the value in place (`sort`, `reverse`, `pop`, `update`, ...) and methods whose result has no JSON form (`encode`, `to_bytes`, ...) aren't ported: they warn at compile time and keep the value (Python TTP saves `None` for the first kind; see `test/comparison/KNOWN_DIFFERENCES.md`).

### Changed (breaking: `upper`, `lower`, `strip`, `lstrip`, `rstrip`, `split`, `replace`, `startswith` and `endswith` are Python's)
These are not TTP match functions, so in TTP they are the `str` methods. gottp's own versions are gone and the methods run instead:
- `split` no longer trims each part, and without an argument splits on runs of whitespace (it split on `,`). `split(",", 1)` and `maxsplit=` work.
- `replace(old, new, count)` honours the count.
- `startswith`/`endswith` take a tuple of prefixes and start/end, and without an argument, or with a list instead of a tuple (`startswith(["a", "b"])`), fail the parse with `TypeError`, as in TTP (they passed).
- `strip(None)` strips whitespace (it stripped the characters `N`, `o`, `n`, `e`).
- `upper`/`lower` use Python's full case mappings.
- On a value that isn't a string (after `to_int`, `split`, ...) they keep the value, as Python's `AttributeError` does. They turned it into a string first.

### Changed (breaking: one function-call reader)
Every function call is now read by one module, `internal/call`, the way Python TTP 0.10.1's `get_attributes` reads it (refactor F1, #36): match variable functions, group attributes and `functions=`/`chain=`, input functions and output functions. Calls are read once, when the template compiles; nothing is parsed per match any more. The separate parsers are gone: `parseFunction` and the quote/comma splitters in the runtime, the match `chain` interpreter, the group `sformatArgs`/`itemize` splitters, and the `default()`, `set()`, `joinmatches()` and `re()` string slicing in the compiler and pattern engine.
- **Arguments are Python call arguments.** Each value is a Python literal: strings with Python's escapes, `r"..."` raw strings and adjacent-literal concatenation, ints, floats, `True`/`False`/`None`, lists, tuples and dicts. A bare word is its own text, and `true`/`false`/`none` in any case are `True`/`False`/`None` (TTP's `_UndefSubst`). So:
  - `re("\\d+")` and `re(r"\d+")` are both the regex `\d+` (#151 item 2, #67). Raw-string arguments to `startswith_re`, `endswith_re`, `exclude_re`, `resub` and the other functions work too.
  - An `=` inside a quoted argument is a character, not a keyword separator: `sformat("v={}")` formats `v=...`.
  - `set(True)`, `set(false)`, `set(5)` and `set(None)` set the bool, int or null, on a line with text and as an unconditional `set()` line (#63). They were strings.
  - Number arguments are read as Python reads them and passed as Python's `str()` of the number (`1.50` is `"1.5"`).
  - Output functions get their keyword arguments in `kwargs` as Python values too, so `traverse(path='a', strict=True)` sees the bool. Positional arguments, and keyword arguments as `key=value` strings, still come in `args`.
- **A `|` inside quotes still splits the chain, as in TTP, and now warns** (#23). `re("UP|DOWN")` is read as the broken calls `re("UP` and `DOWN")` in both TTP and gottp. `GetWarnings()` names the variable, the broken-off pieces and the workaround: define the regex in `<vars>` and pass its name, `re(UP_OR_DOWN)`.
- **Broken calls are compile errors** (TTP stops with `SystemExit` or raises `TypeError`). That covers an unterminated quote or unbalanced brackets inside the arguments, an empty argument (`f(a,,b)`), a positional argument after a keyword one, a repeated keyword, `macro()` with a keyword argument in any scope (`functions="macro(name='m')"`), and an output `macro()` or `macro=""` without a name (#146 item 2). A `functions=` list separated by commas instead of `|` stays an error: it doesn't fit TTP's call syntax, or its brackets don't balance. gottp used to run such calls with whatever its splitters made of them, or skip them silently.
- **An argument that isn't a literal is its raw text, with a warning.** Two cases, both deliberate gottp extensions (see `test/comparison/KNOWN_DIFFERENCES.md`):
  - An unquoted word Python TTP can't evaluate, such as `set(auto-decision)`, `containsall="af-marker"` or `exclude(-VM-)`. Python TTP evaluates it as `auto - decision` and exits. gottp uses the text `"auto-decision"`, and the warning suggests the quoted call, `set("auto-decision")`, which works in both. 8 real templates use this form.
  - A Python expression such as `set(1+2)`, `sformat("a"+"b")`, `x.upper()`, an f-string or `b"x"` (D1). Python TTP evaluates it; gottp passes the text `"1+2"` and warns.
- **Bare names may use any letters**, as Python identifiers do: `contains="Москва"`, `contains(abcé)` and `sformat(é)` work.
- **Python TTP functions gottp doesn't implement warn as "not supported by gottp"**, without suggestions: group `lookup` and `str_to_unicode`, and output `deepdiff`, `validate` and `validate_yangson`. The list comes from TTP 0.10.1's own function tables.
- **Unknown function names warn** (#36). A name that isn't a function of its scope adds a `GetWarnings()` entry naming the scope and the function, with up to three similar names (TTP's `guess`, a port of `difflib.get_close_matches`), and is skipped when the template runs. A match variable keeps its value, as in TTP. A function passed in `CompileOptions.Functions` isn't warned about; one passed only in `ParseOptions.Functions` is, since it isn't known at compile time.
- **One lookup order** for all four scopes: `ParseOptions.Functions`, then `CompileOptions.Functions`, then the built-in functions. Match functions will then fall back to the value's type methods (refactor F2).
- **Several `re()` or pattern names on one variable are alternatives**, as TTP joins them: `{{ intf | re(r"Gig\S+") | re(r"Fast\S+") }}` matches either. gottp used the first.
- **The match `chain(var)` function is expanded when the template compiles only**, as TTP's `extract_chain` does; the runtime `chain` interpreter is gone. Each string of a `<vars>` list chain is split on `|` too.
- **Group attributes are read as the call `name(value)`.** `contains="ip, description"` is `contains(ip, description)`; a keyword argument reaches the function as a `key=value` argument as before.
- `gottp.ValidateTemplate` reads `functions=` with the same reader, so it reports the same syntax errors.
- **`equal` and `notequal` compare by type and value**, as TTP's `data == value`. Now that arguments are Python values, `{{ x | equal(true) }}` doesn't match the text `True`, and `equal(1)` doesn't match the text `1` (after `to_int` it does). The group `equal="x, 1"` attribute is the same, and its value may name a template variable, as in TTP.
- **`re()` without a positional argument is the regex `re`**, as in TTP (`re()`, `re(x=1)`, `re(char="-")`). It matched everything.
- **Group functions with no arguments behave as in TTP:** `contains=" "` and `functions="contains()"` drop every record, `containsall` keeps it, `excludeall` drops it, `del` deletes nothing and `to_int` converts every value. `contains` and `del` used to stop the parse with an error.

### Fixed (template parsing)
- **A template that starts with `<group>` keeps the elements after the first one** (#27). Only the first top-level element was compiled, so a second `<group>`, an `<output>`, `<macro>` or `<vars>` after it was dropped. Python TTP compiles all of them.
- **A template whose XML can't be read fails quickly** (#144). The fallback parser wrapped the text in `<template>` again on every error and started over, growing the text without end, so `<output functions="macro(\"m\",\"n\")"/>` hung the compiler with unbounded memory. The fallback now returns the error. The call reader also bounds its own work: every argument it reads advances the input, and literals nest at most 100 deep.

### Changed (breaking: one per-record group pipeline)
Every record now goes through one pipeline when the record assembler saves it, in the order of Python TTP 0.10.1's `processgrp` (refactor E1, #149; `internal/compiled/pipeline.go`). The order is defaults, then merge_with_last, then the group's functions, then the path. `Parse` (groups with and without children), source maps and `ParseStream` all run the same steps. This replaces the post-assembly code, which ran each group function over all of a group's records and kept `functions=`, `macro=`, `void` and defaults outside the attribute loop. The C2 notes above that say "`functions=`/`chain=`, `macro=` and defaults still run after the attributes" no longer hold.
- **Defaults come before the functions.** Missing variables are filled with `setdefault` before any group function runs, so `record=`, `contains_val=`, `macro=` and the rest see them. The values come from `default=`, each variable's `default()` and unconditional `set()` lines. `default()` and `set()` override a `default=` string, and a `default=` dict overrides everything. **`default()` values now fill every record that lacks the variable**, as in TTP. Before, only the record a group gives when nothing matches had them. A merge_with_last record gets no defaults, as in TTP.
- **`default()` arguments are Python literals.** `default(False)` is `false`, `default(None)` is `null`, `default(5)` is `5`, and `default([])` and `default({"k": 1})` are a list and a dict. `default()` with no argument is `"None"`. A quoted argument is still the string.
- **`contains`, `containsall`, `exclude` and `excludeall` know about defaults**, as in TTP. `contains`/`containsall` don't count a value equal to the group's default for that variable. `exclude`/`excludeall` don't count a variable the group has a default for. Without this, `default=` together with `contains=` would keep every record.
- **One function list in attribute order.** `macro=`, `void`, `functions=`/`chain=` and every other function attribute run at their position in the template. `functions=`/`chain=` expand in place, and so does a `chain=` naming a `<vars>` string or list. The first function that rejects a record drops it. Before, the other attributes ran first, then `functions=`/`chain=`, then `macro=`, and `void` dropped records only at the end. Some examples:
  - `macro="m" contains="mk"` runs the macro first.
  - `void="" record="x"` records nothing.
  - `functions="contains('z')" record="x"` records only the records it keeps.
- **`macro()` inside `functions=`/`chain=` runs**, with one or several names (`macro('a, b')`, `macro(a, b)`). Each item of a `<vars>` list chain is split on `|` too. Together these fix two of #113's three cases.
- **Functions run per record.** A record runs all its functions before the next record starts. So the value a `record=` saves is visible to `set=` in the group's next record, as in TTP. Before, each function ran over every record before the next function started, so `set=` saw only the last recorded value.
- **`itemize` follows TTP** (#88):
  - **Without a path**, the value replaces the record and is saved as an item of a list at the group's path. A `**` path becomes `*`. Attributes after `itemize` still run, where gottp used to return early. They can only drop the item (see `test/comparison/KNOWN_DIFFERENCES.md`).
  - **With a path** (`itemize="key, path"`, `itemize="key='k', path='p'"` or `itemize(key='k', path='p')` in `functions=`), the value goes to that path from the results root, as a list. The path's `{{ variables }}` take the record's values, which are removed from the record. The record itself is kept. gottp used to ignore the path. The keyword form gave an empty list, and `itemize(...)` in `functions=` with a path gave nothing.
  - A group whose `itemize` keeps no record gives nothing, as in TTP. Before, it gave `[]`.
  - `functions="itemize('k')"` no longer flattens a list value (#111).
- **Macro names are looked up in the macro registry directly** (#147, item 1). A template var or recorded var with the same name as a macro no longer stops the macro from running.
- **One kwargs builder.** Every group function gets template vars, then the parse's vars, then the recorded vars. Only built-in functions get gottp's live `_recorded_vars` map and the record's `_defaults`. **A custom group function in `functions=`/`chain=` no longer gets `_recorded_vars`**, which it used to get there (attribute functions already didn't).
- **A top group with a dynamic path drops a record whose path can't be formed.** That is a record where a path variable has no value in the record, the dynamic-path cache, the recorded vars or the vars (TTP's `form_path`). It used to be stored under the literal `{{ variable }}` key. Child groups already did this.
- **Macro error text:** a failing group macro is now `group macro [names] failed: ...` in both `Parse` and `ParseStream`. `Parse` used to add `failed to process group macro: ` in front.
- A group without attribute order (built by hand, or saved by an older gottp) keeps the old function order: the built-in attributes, then custom ones sorted, then `chain=`/`functions=`, then `macro=`, then `void`. Defaults still run first.
- YANG validation runs once per top group after assembly, from one place, on the same data as before.
- **A default value naming a template variable takes the variable's value**, as TTP's `update_groups_runs` does: with `<vars>hostname="R1"</vars>`, `{{ hn | default("hostname") }}` and an unconditional `{{ hn | set("hostname") }}` line fill `"R1"`. A variable passed to the parse overrides the template's. The `_defaults` that `contains`/`exclude` compare against get the resolved value too. (TTP also resolves against values `record()` saved before the input is parsed; that isn't ported.)
- **`default(none)`, `default(true)` and `default(false)`**, in any case, are `null`, `true` and `false`, as TTP's `_UndefSubst` reads them. They were the strings.
- **A Starlark group macro returning `False` drops the record**, in `macro=` and in `macro()` inside `functions=`/`chain=`. The Starlark fast path kept it (`test_group_macro_returns_false` now passes).
- **`sformat(string=..., add_field=...)` in `functions=`/`chain=`** saves under `add_field`. It made a key named `add_field=nv`. Positional arguments now work in the `sformat=` attribute too.
- **`items2dict` drops a record without one of its keys**, as in TTP. It kept it unchanged.
- **Group pipelines are built once per `CompiledTemplate`** and shared by its parses, not rebuilt on every parse. A parse rebuilds them when its vars name a variable a `default=`, `chain=` or default value resolved, or when `ParseOptions.Functions` has group functions. Whether a macro step can take the all-Starlark fast path is now decided when it runs.

### Changed (breaking: text outside any group)
- **Text outside any `<group>` is parsed only in a template without XML tags**, as in Python TTP 0.10.1 (`ttp/ttp.py` `construct_etree`, `if not list(template_ET)`). A template that is only text is still an implicit `_anonymous_` group. With any tag present (`<vars>`, `<macro>`, `<doc>`, `<input>`, `<output>`, `<lookup>`, `<group>`, or a `<template>` with tags inside) that text is now ignored and gives no results (`{}`); gottp used to parse it as an implicit group whenever the template had no `<group>`. `CompiledTemplate.GetWarnings()` names the first ignored line: `top-level text outside any <group> is ignored because the template has XML tags (as in Python TTP): "<line>"`. Put the text inside a `<group>` to keep parsing it. The text of a nested `<template>` (inside another `<template>`) is always ignored, as in TTP. An `<extend>` of a template that is only text appends that text to the template's own, as TTP's `handle_extend` does, so a template whose only tags are such extends still parses it, once. (#31)

### Fixed (template variables)
- **`ignore("<vars name>")` works**: it ignores the variable's regex, as `re("<vars name>")` matches it. gottp emptied the group instead (`{"g": {}}`), a rule it took for a Python TTP quirk; TTP's actual rule is the one above about text outside any group. The rule's code is gone from the pattern engine, the runtime, the source map and the streaming gate, so these groups now stream. (#31)
- **An unknown tag counts as a tag** for the rule above: with a well-formed unknown element such as `<foo>bar</foo>` or `<foo/>` at the start of a line, text outside groups is ignored, as in Python TTP (which logs "invalid tag"), and `GetWarnings()` names the tag. A bare `<` in template text, such as `for <{{ vr }}>`, is still read as text.
- **`<vars>` values are evaluated as Python literals**: `"\\s+\\S.*"` is the regex `\s+\S.*`, as is `"\s+\S.*"` (Python keeps an unknown escape), and `r"Channel\d+"` keeps its backslashes; `\t`, `\n`, `\xNN`, `\uNNNN`, octal escapes, adjacent literals and one-line triple quotes are decoded too (multi-line strings and tuples, `\N{...}` and `b"..."` are not). A double-backslash regex in `<vars>` used to match a literal backslash, so the group returned `{}`, and an `r"..."` value kept its `r"` prefix. A `<vars>` dict or list that isn't JSON once converted (a `\d` in a string, a trailing comma) is now loaded too (#90's case). (#148)
- **An inline `ignore()` argument is a Python string**, and its regex is used as written: `ignore("[\d]+")`, `ignore("[^\s]+")` and `ignore(r"\s+")` work. gottp rewrote `\d`, `\s` and `\w` into character classes, which broke them inside `[...]`.

### Fixed (outputs)
- **Output macros run**: `<output macro="name"/>` and `<output functions="macro('name')"/>` were ignored, so the results came back unchanged. They now run the macro on the whole results, like Python TTP 0.10.1's output `macro()`: the macro gets the per_input list of results (or the per_template result), and what it returns replaces them, `True` and `False` included; `None` keeps the results with any in-place change. `macro=` and `functions=` run in attribute order, before the formatter. An undefined macro is skipped; a macro that fails is a parse error. `macro="a, b"` and `macro('a', 'b')` run each macro in order; this is a gottp extension, since Python TTP 0.10.1 raises `TypeError` on both. Native Go macros work on per_template results; they take a map, so on the per_input list they are an error. A per_input result that an output macro or function turns into a non-list (a dict, `False`) is no longer wrapped in one more list; formatter output keeps its wrap (#98). (#142)

### Changed (breaking: groups with child groups)
A top group with child groups is now parsed as Python TTP 0.10.1 parses it (refactor C2, #60; `internal/compiled/tree.go`). All the matches of the group and its descendants go into one stream, sorted by position, and one record assembler (the `_results_class` port from C1) turns them into records. Each record is saved at its path under the last record of its parent group, with a port of TTP's `save_curelements`. gottp used to parse the parent alone, guess an input range for each parent record (five rules, then an even split of the input), and parse every child group again on each range. Those ranges, the re-parse and the old merge (`stepMerge`) are gone. Templates that relied on them change results:
- **Children only see their parent's region.** A child group's patterns run from the parent's first start line to the parent's last `_end_` (or the end of the input). Child lines before the parent's first start are dropped. Between parent records, a child line goes to the last parent record. After a parent's `_end_`, child lines are dropped until the parent starts again.
- **One template line per data line, across the whole tree.** The C1 rule (#32) now also applies between a parent and its children and between siblings. At one position a start line beats an ordinary one, and among equals the current record's group wins, then a child of it or a group whose parent has started. A sibling's `_start_` ends the previous sibling's record, so a joinmatches line stops collecting there (#118), and a group's second `_start_` line no longer matches inside a sibling's section (#119).
- **A parent whose start line has no values keeps its record**, so its children are kept (`Header {{ _start_ }}`, `{{ ignore | _start_ }}`). A parent record that ends up empty is saved as `{}`, as TTP saves it. (#28)
- **A group with only child groups** gives its children's records (#89), and **anonymous child groups** are separate records at their parent's path, as in TTP; their records used to be merged into the parent record (#89). Sibling groups with the same name form a list (#120). A child group with `default()` values gives its record of defaults when nothing matches, even when the parent matched nothing (#91).
- **Values on an `_end_` line are discarded** in groups with children too (#128).
- **A parent's lines after a child record** (a line after `</group>`, or a parent line that comes after the child's lines in the data) are merged into the parent's last record, overwriting values it already has (TTP's `merge_with_last`).
- **A record is post-processed when it is saved, a parent before its children.** Group functions, `chain=`, `macro=`, defaults and `record=` of a parent run on the parent's own values only; they no longer see the child records. A `record()` in a parent is now visible to its children's `set=` (#99). `itemize` on a child group now gives the list of values at the child's path (#88; the path argument is still ignored).
- **Child paths resolve as in TTP.** A `{{ variable }}` in a child group's name takes the child record's value, then a value an earlier record's path used (the dynamic-path cache), then a template variable. A child record whose path can't be resolved is dropped; it used to be stored under the literal `{{ variable }}`. **An absolute child path is a path from the results root**, as TTP's `save_curelements` saves it. `name="/vlans"` under a top group `intf` gives `{"intf": [...], "vlans": [...]}`, collecting the records of every `intf` record in one list. gottp used to put them under a literal `"/vlans"` key in each parent record. This holds for grandchildren too, and a relative child of an absolute group goes below it. An absolute path that names the top group's own path (`name="/interfaces*"`) saves the records there. `name="/"` saves at `_anonymous_*`: the records become items of the input's result list, and the rest of the results become one more item. Under an anonymous top group, `name="/vl"` gives one more item, `{"vl": [...]}`. Under a parent whose path has an `_anonymous_` segment, the path goes below `_anonymous_*`, as in TTP.
- **The children of a `void` top group are kept**, saved from the results root as in TTP, where `void` drops only the group's own records. gottp used to drop the whole tree.
- **Child group functions see only template and recorded variables (breaking).** A child's `default=`, `contains_val=`, `exclude_val=`, `macro=`, `set=` and other group functions resolve names against template variables, values recorded with `record()` or `record=`, and the parse's vars, as in TTP. Until now they also saw the last parent record's values. So `contains_val="vname, name"` compared with the parent's `name`, `default="desc"` gave the parent's `desc` value, and a macro whose name matched a parent key (a child `fan*` with `macro="fan"`) was skipped once the parent held its records, which left the last child record unprocessed. A child that needs a parent value must `record` it in the parent.
- **The `record=` group attribute records the variable**, as TTP's group `record` function does: `record="vrf"` (or `record="vrf, target"`) makes the record's value visible to later groups' `set=` and other functions and to paths. It no longer merges records (see below).
- **Removed gottp-only rules**: the per-parent input ranges and their even-split fallback; re-parsing each child group once per parent record; deleting a parent variable when a child record held the same value; a group without lines of its own returning its first anonymous child's results.
- **Empty records follow TTP's `save_curelements` in every group.** A first empty record is filled by the next record, an empty record right after the first one becomes a list item, and after that empty records are left out. A lone empty record gives `{}` at the group's path (`{"g": {}}`); gottp used to drop every empty record. A record whose only value is `_line_` is kept. `ParseStream` still emits no empty records.
- `expand` now handles keys without a dot before dotted ones, so `config` and `config.mtu` on one record give the same result every run (it depended on Go map order).

### Changed (breaking: `record=` and group function attribute order)
In every group, with or without child groups:
- **`record=` no longer merges records.** gottp used to merge all of a group's records that had the same value of the record variable into one record, turning differing values into lists, a gottp-only rule: TTP's group `record` function only saves the variable. With `record="x, tgt"` it looked up a variable named `x, tgt`, so it merged every record into one. Each record is now kept, as in TTP. A template that relied on the merge gets one record per match; group them in your own code, or with a dynamic path (`name="vrfs.{{ vrf }}"`).
- **Group function attributes run in template order**, as TTP runs them, and stop at the first one that drops the record. `record=` is one of them: with `contains="z" record="x"` a record that `contains=` drops records nothing, where gottp used to record before every other function. Built-in attributes (`contains=`, `del=`, `set=`, `sformat=`, ...) used to run in a fixed order, so `del="z" contains="z"` kept records TTP drops; attributes naming a custom group function used to run after the built-in ones, in random order. `functions=`/`chain=`, `macro=` and defaults still run after the attributes.

### Changed (source map content: groups with child groups)
Parsed data is the same with source maps on and off. The `SourceMap` JSON shape doesn't change. Match positions are now offsets in the whole input for every group (the observer used to add each child range's offset). Content changes for groups with children:
- **Lines the new records use are recorded**: a parent start line without values (#28), lines of groups that used to be dropped (#89, #91, #119), and lines of an itemized child group (#88), whose `ResultPath` used to be empty.
- **One match per line.** A data line that several groups' patterns matched used to be recorded once per group; it is now recorded for the winning group only.
- **`ResultPath` follows the new results**: list indices where siblings with the same name or anonymous children form a list (`vrfs.rts[0]`, `p[1]`), no doubled levels for `**` paths (`bgp` instead of `bgp.bgp[0]`), and the right parent record (`router_lsa[1]`, which used to be `[0]`). A `_` (null path) segment never appears in a path.
- **A line that only an unconditional `set()` line matched is no longer recorded**: TTP has no regex for such a line.
- Records of `void` groups, and empty records a list leaves out, keep an empty `ResultPath`.

### Changed (breaking: record assembly)
A group without child groups is now assembled by a port of Python TTP 0.10.1's `_results_class` (refactor C1, #60; `internal/compiled/assembler.go`). `Parse`, source maps and `ParseStream` all use it. Refactor C2 (above) moves groups with children onto it. Templates that relied on these gottp-only behaviours change results:
- **One template line per data line (first match wins).** When several template lines match the same data line, TTP uses one of them: a `{{ _start_ }}` line first, then other start lines, then ordinary and `_end_` lines, then `_line_` lines. Within a tier the first template line wins, with `_end_` lines ahead of ordinary ones. gottp used to fill the record from every line that matched. A line made only of `ignore` variables still takes its data line. Python TTP turns digits in a line's text into `\d+`, so `Field-01 {{ a }}` and `Field-02 {{ b }}` both match `Field-07 x`, and the first one now takes every such line. Give such lines distinct text. (#32)
- **Values on an `_end_` line are discarded.** The line only ends the record. gottp used to save them. (#128, for groups without children)
- **joinmatches keeps value types.** Strings are joined with the join character, lists are extended (`split(",") | joinmatches` gives one list), and any other value becomes a list (`to_int | joinmatches` gives `[5, 6, 7]`, or `5` for one match). gottp used to stringify everything into one string. On a joinmatches line, TTP also joins the line's other variables. (#34)
- **A repeated start line starts a new record**, including one with a joinmatches variable and a joinmatches first line. gottp used to keep merging into the current record. (#29)
- **A start line rejected by a condition (`exclude`, `contains`, ...) ends the current record.** The lines after it are dropped until the next start line. gottp used to attach them to the previous record. (#69)
- **`_line_` loses its data line to every other template line**, so it no longer captures the start line. `_line_` joins lines even without joinmatches. A `_line_` line rejected by a condition is skipped instead of stopping later lines from joining. (#79)
- **No line-gap limit.** A line more than 100 lines after its record's start line is added to the record, as in TTP. gottp used to drop it (`maxGapLines`, a gottp-only rule).
- **Ties between two start lines on one data line follow TTP.** Before a group's first record, the last matching start line wins. After that, the first one does. A rejected start line that is the last candidate ends the group, as in TTP.
- **A `{{ _line_ }}` variable keeps its value.** A line that is only `{{ _line_ }}` compiled to a regex without a capture group, so the joined lines never reached the record; they are now saved under `_line_`, as in TTP.
- `ParseStream` `srcRange` follows the new records. A record closed by `_end_` ends at the end of that line, not at the next record's start, and a record ended by a rejected start line ends where that line starts.

### Changed (breaking: ParseStream)
- **`ParseStream` refuses templates it used to stream incorrectly**: its gate accepted group features the stream path doesn't implement, so those templates streamed without an error and gave records that differ from `Parse`. `ParseStream` now returns `ErrTemplateNotStreamable` (as `*TemplateNotStreamableError`, with one reason per feature) before calling the callback when a top-level group uses any of these: `chain=`/`functions=` functions outside the streamable allowlist, including after a `|` and in a `<vars>` value a chain names; group functions given as attributes (`contains=`, `containsall=`, `del=`/`delete=`, `exclude=`, `excludeall=`, `equal=`, `to_int=`, `contains_val=`, `exclude_val=`, `sformat=`, `itemize=`, `set=`, `expand=`, `items2dict=`, `to_ip=`, `record=`), or an attribute naming a custom group function from `CompileOptions` or `ParseOptions`; `default=`; `void`; `set()` defaults on a line with no other text; `method="table"`; a dynamic path (`{{ }}` in `name=`); `ignore()` with a template variable; a pattern that isn't line-anchored (this failed during the parse before). Detect it with `errors.Is(err, gottp.ErrTemplateNotStreamable)` and fall back to `Parse`, or check up front with `gottp.WhyNotStreamable`, which lists the compile-time reasons. Custom group function attributes, and a chain variable overridden by the parse's vars, are known only when `ParseStream` starts, so only its error reports them. A template affected by this change already gave wrong records. (#130)

### Fixed (ParseStream)
- **A start line with `default()` streams the record of defaults** `Parse` gives when the group matches nothing, with `srcRange` `[0, 0]` and the group's path. (#130)
- **A record that its chain functions empty is dropped**, as `Parse` drops it; the stream gave `{}`. (#130)
- **`chain=` naming a template variable is checked against the variable's value** (a string chain or a list of functions), not the variable's name. (#130)

### Changed (breaking: result shape)
- **Top-level anonymous groups now match Python TTP's result shape**: a template whose top-level group has no `name` (an unnamed `<group>`, or a template with no group tags at all) used its list of matches as the *whole* per-input result list, so the result was one list level short (`[[{...},{...}]]` from `NewParser().Result()` instead of TTP's `[[[{...},{...}]]]`), every input after the first was dropped, and named groups next to the anonymous one were lost. Each input's result is now built the way TTP's `form_results` does it: the anonymous matches are that input's result, other top-level results in the same input are appended as one more item, and every input keeps its own entry. An unnamed `<group>` gives a list even for one match; a template without group tags is an implicit group named `_anonymous_` (as in TTP), so one match gives a dict. The same applies to `results="per_template"` and to the source-map path (`EnableSourceMap`), whose `per_template` result kept a literal `_anonymous_` key. The `table` formatter flattens the per-input lists into one table as before. Code that reads `result[0]` as a match dict for an anonymous-group template must now read `result[0][0]`. Source maps report `GroupName: "_anonymous_"` for the implicit group; `ParseStream` still reports an empty `groupPath` for it. (#62)

### Fixed
- **`strip`/`lstrip`/`rstrip` characters argument**: `strip("chars")` ignored its argument and only removed whitespace, and `lstrip`/`rstrip` weren't registered, so all three returned the value unchanged. They now behave like Python's `str.strip/lstrip/rstrip(chars)`: the argument is a set of characters removed from both ends, the start or the end, and without an argument they remove whitespace. The `chain()` fallback does the same. A quoted argument made only of the other quote character (`strip('"')`) also reached the function as an empty string; quote characters inside a quoted argument are now kept. (#35)

### Changed (breaking: matching)
- **Indented template lines match the exact indent**: a template line's leading whitespace was turned into `[ \t]+`, so a line indented by two spaces also matched data indented by one space, four spaces or a tab. Python TTP rebuilds the indent verbatim, and gottp now does the same: two spaces match exactly two spaces, and a tab matches only a tab. Unindented lines are unchanged, and so is whitespace inside a line, which still matches any run of spaces and tabs. Templates that relied on the loose match need their indent to match the data. Templates saved with `SaveCompiledTemplate` keep the regex they were compiled with until they are compiled again. (#30)

### Changed (stricter YANG validation)
These fixes make `ParseWithValidation` report problems it used to pass, so output that was `Valid=true` can now be `Valid=false`. Parsed data is unchanged; only `ValidationResults` differ.
- **Integer leaves reject fractional numbers**: `12.5` no longer validates as a `uint8` (RFC 7950 9.2). A whole `float64` such as `12.0` (what a JSON round trip makes of an int) is still accepted. (#50)
- **`pattern` is enforced**: a string leaf must match all its patterns as a whole value, with XSD regex semantics (RFC 7950 9.4.5), and `modifier invert-match` is honoured. Patterns RE2 can't express (`\i`, `\c`, `\p{IsBlock}`, class subtraction) give a warning, once per group, instead of passing silently. (#55)
- **Enumeration and identityref membership is checked**: an enum leaf takes only its declared names, and an identityref only an identity derived from its base, in the RFC 7951 `module:identity` form (the module may be left out for an identity in the leaf's own module). A `union` with an enum member no longer accepts any string. (#56)
- **A `yang=` path at the wrong level is an error**: when none of a group's fields is defined under its path (for example the container instead of the list each match maps to), the result is `Valid=false` with one error that suggests the right path, instead of `Valid=true` with only warnings. (#57)
- **Leaves under `choice`/`case` are validated**: they were reported as "not defined" warnings and never type-checked. (#59)

### Fixed (source maps on)
`ParseOptions{EnableSourceMap: true}` (the editor's source-map toggle, and `ParseWithValidation` callers that set it) ran its own copy of the parse orchestration, which had drifted from the one used with source maps off. Both now run one pipeline (refactor A1, #60), so turning source maps on no longer changes data, errors, key fields or validation results:
- **A group without `input=` parses every input**, not only `Default_Input`, and `input="a, b"` is split on commas. Inputs embedded with `<input load="text">` or passed under other names gave an empty result. (#105)
- **Group errors keep their `failed to parse group <name>:` prefix.** (#106)
- **The `ignore("<vars name>")` empty-record special case applies**, so the group comes back as `{}` instead of being dropped (as with source maps off; #31 tracks matching Python TTP). (#107)
- **`void` groups are left out of the results.** (#108)
- **Input functions run** (`<input>` `functions=`, `macro=`, `commands=`), and **`KeyFields` is filled** from `keys=`.
- **Top-level groups are validated once.** A second YANG validation of top-level groups, which replaced the result `parseGroup` recorded, is gone; a group that only returns its start-line defaults no longer gets a validation result that it doesn't get with source maps off. (#52)
- `<vars name="...">` tags are stored the same way as with source maps off: in each input's results with `results="per_input"` (with getters such as `gethostname` resolved), and not at all with `per_template`.

### Changed (source map content)
The source map is now recorded from the matches the parser actually uses, instead of a second matching pass after parsing (refactor A2, #60). Parsed data doesn't change. The `SourceMap` JSON shape doesn't change, but its content does:
- **`ResultPath` is the record's real location in the results**, found by following each record through `record=`, group functions, macros and storing. Every level gets its list index: `routers[0].interfaces[1].addresses[0]`, where it used to be `routers*.interfaces[1].addresses`. Dynamic paths are resolved (`vlans.10` instead of `vlans.{{ id }}[0]`), and a repeated group with one match gives `interfaces[0]` instead of `interfaces*`. The old pass looked the path up by prefix in random map order and recorded only two nesting levels.
- **Only matches a record used are recorded.** A line a pattern matches but no record takes (before the first start line, after a rejected start line, a redundant `_start_`/`_end_` match) is no longer marked matched.
- **Matches of records that don't reach the results** (filtered out by `contains=` and similar, `void` groups, a child group whose `itemize` result isn't stored) are still recorded, with an empty `ResultPath`.
- **Children at every depth are recorded**, including a line that two groups' records both consumed.
- With source maps on, parsing is 24–32% faster and allocates 2–20% less, because the second matching pass is gone.

### Fixed (streaming)
- **`ParseStream` refuses templates it would parse differently from `Parse`.** Its streamability gate accepted group features the stream path ignores, so those templates streamed without error and gave different records. `WhyNotStreamable` now reports, and `ParseStream` returns `*TemplateNotStreamableError` for, these features: `chain=` functions outside the allowlist (only `functions=` was checked); a non-allowlisted function after a `|` (the names were split on commas only, so `contains('ip') | itemize(...)` passed); group functions given as attributes (`contains=`, `record=`, `expand=`, ...); `default=`; `void`; `set()` defaults; `method="table"`; dynamic paths; `default()` on the start line; `ignore()` with a template variable; a pattern that isn't line-anchored (it used to fail at runtime); and an attribute naming a custom group function (checked when `ParseStream` starts). A streamed record emptied by its group functions is now dropped, as `Parse` drops it. (#130)

### Fixed
- **SourceMap ResultPath for repeated groups**: `MatchMapping.ResultPath` for a repeated group (`name="interfaces*"`) always came back as the literal, unresolved group-name pattern (`"interfaces*"`) for every match, instead of resolving per-instance (`"interfaces[0]"`, `"interfaces[1]"`, ...) as documented. Per-match instance boundaries are now derived from the already-collected, position-sorted match list, with a safe fallback to the previous behavior for merge modes (table method, joinmatches) the boundary heuristic doesn't model. (#24)
- **Silently-swallowed group macro failures**: a group macro that failed — whether its source didn't compile as Starlark at all (e.g. `del data[key]`, unsupported by this version of go.starlark.net) or it threw at call time on a specific record's data — was silently treated the same as an unregistered macro name, with the match falling back to completely unmodified data and no error or warning anywhere. `ValidateMacroSource` now actually attempts to compile macro source as Starlark, surfacing genuine syntax errors as a compile warning; `processGroupMacro` now distinguishes "macro not registered" (still silently skipped, matching Python TTP behavior) from a real execution failure of a macro that *was* found (now propagates as a parse error). (#26)
- **Stale SourceMap.Variables after macro field rename**: a group macro that renamed a field (`data["name"] = data["ifname"]`) left `SourceMap.Variables` only keyed by the pre-macro name, with nothing connecting the renamed field in the final output back to the source span it came from. Renamed fields are now reconciled by value per resolved instance and aliased to their original span; macro-fabricated fields with no matching pre-macro value correctly still get no provenance entry. (#25)

## [v0.1.12] - 2026-07-25

### Performance
- **parseGroup Parent Ranges**: Removed two O(parents × matches) rescans of the match list in `parseGroup`'s parent-range computation. `allMatches` is already sorted by position, so both lookups are now binary searches. Parse time is linear in record count again instead of quadratic: on an 80,000-row input, ~1986 ms → ~130 ms (15×). Production profiles had this block at ~17% of aggregate CPU and ~50% within a single 30-second window.
- **Parent Span Bookkeeping**: Parent-to-match index lists are stored as `{lo, hi}` ranges rather than materialized `[]int` slices, cutting allocations on the same 80,000-row input from 4.32M to 1.28M (−70%) and 426 MB to 164 MB (−62%).
- **Dynamic Path Resolution**: The `{{ variable }}` regex in `PathResolver` and `ResultManager.FormPath` is compiled once at package scope instead of on every call, and placeholder substitution no longer compiles a second regex per placeholder. This accounted for ~7% of all allocations in production profiles and affects every template with a named group, not just dynamic paths.

### Fixed
- **Dynamic Path Values Containing `$`**: A parsed value containing `$` was silently truncated when substituted into a dynamic group name — `{{ hostname }}` resolving to `r$1x` produced `r`. Substitution used a regex replacement, which expanded `$1` / `${name}` sequences inside the replacement text; it now inserts the value verbatim.

### Also included (previously unreleased)

These entries had been accumulating under `[Unreleased]` and ship with this tag.

- **Start Pattern Detection**: Fixed issue where non-start patterns (like `route-policy`) were matching even when the `_start_` pattern didn't match. Now, when `_start_` is present but `_end_` is not:
  - Patterns with `_start_` are always start patterns
  - Patterns before the first `_start_` pattern can also be start patterns (if they have non-special variables)
  - Patterns after the first `_start_` pattern are not start patterns and only merge into matches started by `_start_` patterns
- **Empty Match Filtering**: Added logic to filter out empty matches from `mergedMatches` before returning from `parseGroup`, preventing empty maps from appearing in results
- **Traverse Function**: Fixed `traverse` function to correctly wrap dict results in lists when traversing paths in `[{interfaces: {...}}]` format, ensuring consistent return types
